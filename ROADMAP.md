## Уточнения из официального текста (важно учесть при доработке!)

### Присваивание — 6 вариантов (сейчас реализован только №1)
1. A=expr — готово
2. A[]=expr — неявный цикл по одномерному индексу (?), требует SIZE — код есть, не активен
3. A[,]=expr — неявный цикл по двум индексам (?1,?2), требует SIZE — код есть, не активен
4. A:константа — короткая форма с плавающей точкой (A:-6.02e-23) — НЕ РЕАЛИЗОВАНО
5. A:$?[индекс] — присвоить код символа из строки — НЕ РЕАЛИЗОВАНО
6. A#$0 — вычислить выражение, находящееся в текстовой переменной, и присвоить
   результат — НЕ РЕАЛИЗОВАНО (интересный кейс: интерпретатор внутри интерпретатора)

### Присваивание строк (текстовых переменных) — НЕ РЕАЛИЗОВАНО
- $I=$J+'текст'+A (конкатенация через + текстовых переменных, констант и чисел)
- $?[индекс]=выражение — присвоить код символа внутри строки по индексу

### Строковые переменные — важное уточнение!
- $0-$9 — переменные ПРОИЗВОЛЬНОЙ длины (до 1024 символов) — уже реализовано
- $A-$Z — это элементы СТРОКОВОГО МАССИВА фиксированной длины 75 символов
  (до 850 элементов), т.е. $A эквивалентно $[1], $B эквивалентно $[2] и т.д.
  Это ДРУГАЯ структура данных, не 26 отдельных переменных! Нужен единый массив
  static_strings[850][75], а буква просто маппится на индекс.

### Метакоманды (!nul, !one, !err) — НЕ РЕАЛИЗОВАНО
- !nul, !one, !err в начале строки управляют поведением при 0/0 в выражениях
  (по умолчанию !err — выдать ошибку). Нужно добавить флаг в InterpreterState
  и проверять его в expr.evaluate при делении.

### Условие ESLI — обнаружен второй режим сравнения (**), не только (%%)!
- ESLI X ** {Y,Z} C — X принадлежит диапазону [Y,Z] включительно
- ESLI X ** }Y,Z{ C — X НЕ принадлежит диапазону (Y,Z) исключая границы
- ESLI P%%F C — сравнение ТЕКСТОВЫХ переменных/констант (P,F), не только чисел!
  Текущая реализация execEsli поддерживает только числовые %%, нужно добавить:
  1) сравнение строк, 2) режим ** с диапазоном {}/{}

## Разбор пробелов для запуска sample.ela — 04.08.2026 вечер

Полный разбор оригинального демо-файла автора языка показал, какие
операторы реально нужны для его выполнения (помимо уже готового ESLI,
SIZE, DLIN, FIND, %CHR, INCR/DECR, присваивание всех 6 вариантов).

### Группа 1 — быстрые победы (低 effort, без внешних зависимостей)
- [ ] KEYS A       — код нажатой клавиши без ожидания (0 если не нажата)
- [ ] WAIT [A[#]]  — ждать нажатия клавиши, опционально в переменную
- [ ] SUMA D;S      — сумма элементов одномерного массива
- [ ] MINA D;I      — индекс минимального элемента
- [ ] MAXA D;I      — индекс максимального элемента
- [ ] DATA A;B;@label — заполнить строковый массив из строк программы

Для KEYS/WAIT нужен неблокирующий (KEYS) и блокирующий (WAIT) опрос
клавиатуры на Windows — реализуется через consoleapi (_kbhit/_getch
аналоги) или WinAPI ReadConsoleInput, без графики.

### Группа 2 — файловые операторы (умеренный объём, стандартный I/O)
- [ ] LENF F;L     — длина файла
- [ ] UDAL F       — удаление файла
- [ ] PATH F       — полный путь из маски/имени
- [ ] FILE F;N     — поиск файлов по шаблону в текстовый массив
- [ ] FREE D;L     — свободное место на диске
- [ ] SORT $;N;F / SORT A;N;F — сортировка строкового/числового массива
- [ ] TYPE F;список — запись в текстовый файл (как LIST, но в файл)
- [ ] PUTF/GETF F;... — чтение/запись двоичных файлов

Все реализуемы через std.fs без сторонних зависимостей.

### Группа 3 — интерфейс
- [ ] MENU N;L;S;C;F — многостраничное текстовое меню
  (зависит от Группы 1: KEYS/WAIT для навигации)

### Группа 4 — самое трудное: полноценная графика (9 операторов)
- [ ] GRAF (реальный режим 640x480x16, не заглушка)
- [ ] PIXL, RDOT, CVET, LINE, RAMA, MOVE, KRUG, PAIN, SBMP

sample.ela почти наполовину состоит из рисования (раздел @grafika,
радуга @raduga, счётчик точек по цвету через RDOT). Без реального
рендеринга эта часть физически не может работать.

Архитектурное решение: создание окна и растровая графика на Windows
без внешних зависимостей — через WinAPI (CreateWindow + GDI:
SetPixel/Rectangle/Ellipse/BitBlt для SBMP). Это на порядок больше
кода, чем всё, что сделано в проекте до сих пор — отдельный крупный
этап, не встраиваемый "по пути".

### Группа 5 — численные методы (математический блок)
- [ ] REAK X;Y;A;B;C;R;F — нелинейная регрессия A*X^B*exp(-C*X)
  (используется в разделе @matem для аппроксимации точек)
  Требует итерационного численного метода (напр. Гаусса-Ньютона).

  test_menu_graf_loop.ell (включая MENU из консоли, управляющий
  графикой в отдельном окне, с многократным выбором в цикле)

**Группа 5 — REAK (нелинейная регрессия) — ЗАВЕРШЕНА**
- REAK X;Y;A;B;C;R;F — модель Y=A·X^B·exp(-C·X), метод Гаусса-Ньютона
  с демпфированием (Levenberg-Marquardt), решение нормальных уравнений
  3×3 методом Гаусса с выбором главного элемента
- R — корреляция Пирсона (факт/модель), F — RMSE остатков
- Защита от вырожденных случаев: X[i]≤0 → RuntimeError.MathDomainError,
  A≈0 на входе → авто-подстановка 0.01 перед первой итерацией
- Проверено на реальном фрагменте из sample.ela (300 точек,
  A:10;B:6;C:2 + шум &ran#): получено A≈10.5, B≈5.7, C≈1.9, R≈0.998,
  F≈0.29 — совпадает с независимым Python-прототипом на той же модели

### Побочные исправления (обнаружены при тестировании графики/REAK)

- **Насос сообщений Win32**: main.zig не вызывал graphics.pumpMessages(),
  из-за чего графическое окно уходило в "Не отвечает" на любой
  блокирующей операции (WAIT, MENU). Исправлено: pumpMessages() в
  основном цикле интерпретатора + перевод WAIT/MENU с блокирующего
  ReadConsoleInputA на неблокирующий поллинг (PeekConsoleInputA +
  Sleep(10) + pumpMessages() на каждой итерации). shouldForceExit()
  подключён для корректного завершения при закрытии окна крестиком.
- **Лексер: числа без ведущего нуля** (`.011`) не распознавались —
  next() вызывал lexNumber только при isDigit(c), точка как первый
  символ токена падала в UnexpectedCharacter. Исправлено добавлением
  проверки `c == '.' and isDigit(peekAt(1))`.
- **expr.zig: `X[]` как значение выражения** — синтаксис пустых
  скобок (сокращение "по индексу текущей неявной итерации", как `?`)
  поддерживался только слева от `=` (is_implicit_1d в execAssignment),
  но не распознавался парсером выражений на правой части (`Y[]=...X[]...`).
  Исправлено в parseIdentifierExpr: `[]` теперь строит тот же узел,
  что и явный `[?]`, без изменений в evaluate().

### Находка по документации — ESLI обновлён раньше, чем отражено в roadmap

В реальном коде `execEsli` (statement.zig) уже полностью реализованы:
- `ESLI X {Y,Z} C` / `ESLI X }Y,Z{ C` — диапазоны включительно/исключая
  (через lbrace/rbrace, режимы eq_eq/pipe_eq)
- `ESLI $P == $F C` / `ESLI $P |= $F C` — сравнение текстовых переменных

Это ранее считалось пробелом в старой версии roadmap (Приоритет 3) —
на самом деле уже сделано, просто не было отдельного unit-теста и не
обновлён статус документа. **Рекомендация**: написать короткий
test_esli_ranges.ell, чтобы формально закрыть пункт, а не просто
считать его готовым по факту наличия кода.
